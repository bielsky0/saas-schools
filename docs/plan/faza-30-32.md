**Status:** ✅ zakończona (2026-07-26)

## Faza 30b — CMS: edytor stron + core bloki + renderer

**Status:** ✅ zakończona (2026-07-26)
**Cel:** Admin akademii tworzy/edytuje/publikuje strony przez Payload Admin UI z blokami core. Strony renderowane publicznie.
**Zależności:** Faza 30a (schemat gotowy, izolacja zweryfikowana).
**Migracja:** Payload może wygenerować nową migrację po zmianie konfiguracji kolekcji `pages`.

### Zakres

- Kolekcja Payload `pages` z polami: `slug`, `title`, `status` (`draft`/`published`), `blocks` (konfiguracja bloków)
- Core bloki (CMS spec §2.6): `Grid` (1/2/3/4 kolumny, odstępy small/medium/large), `Column` (kontener na zagnieżdżone bloki), `Text`, `Button` (warianty primary/secondary/outline, rozmiary small/medium/large), `Image`, `Separator`, `Accordion`
- Słownik stylowania (CMS spec §2.7): opcje z dropdownów (np. `size: "large"`) → klasy Tailwind mapowane w kodzie. **Zakaz przechowywania klas Tailwind w bazie.** Jedna zmiana w słowniku = zmiana globalna w całym SaaS, zero migracji.
- Renderer: `[...cmsSlug]/page.tsx` → lookup `page` po `(organizationId, slug)` + `status = 'published'`. Rekurencyjny render z limitem głębokości 10. Nieznane typy bloków renderowane jako `<div>Unknown block</div>`.
- Strona główna: slug `""` → renderowana na gołej subdomenie akademii (CMS spec decyzja #8) przez `[locale]/page.tsx` z gałęzią `servedSubdomain()`.
- Walidacja slugu: `isReservedSlug()` blokuje zarezerwowane prefiksy.
- Walidacja bloków: rekursywnie przy zapisie — funkcja `validateBlockAccess(blocks, grantedKeys)` z limitem głębokości 10. Nieznane bloki → invalid. Core bloki → zawsze valid (granty ignorowane). Custom bloki → wymagają klucza w `grantedKeys` (przygotowane na 30d, dziś nie ma custom bloków w rejestrze).

## Faza 31 — Ochrona przed overbookingiem: `bookings.release_expired_pending`

**Status:** ✅ zakończona (2026-07-27)
**Cel:** Booking z `paymentStatus = 'payment_pending'` starszy niż 15 min jest automatycznie anulowany (seat released). Niezależna od CMS.
**Zależności:** Żadna — job dodawany do istniejącej infrastruktury jobów.
**Migracja:** Żadna — nie dotykamy schematu. TTL liczony od `created_at`.

### Mechanizm

Wzorzec joba: `credits.expire` (`src/features/credits/expire.ts`).

1. **SELECT** z narrow system bypass (lista bookingów):
   ```sql
   SELECT b.id, b.organization_id, b.session_id
   FROM booking b
   WHERE b.payment_status = 'payment_pending'
     AND b.created_at < now() - interval '15 minutes'
     AND NOT EXISTS (
       SELECT 1 FROM group_change_request gcr
       WHERE gcr.resulting_booking_id = b.id
         AND gcr.status = 'awaiting_payment'
     )
   ORDER BY b.created_at
   LIMIT 500
   ```
2. **Grupowanie per tenant** (mapa `organizationId → ids[]`)
3. **UPDATE** per tenant wewnątrz `withTenant`:
   ```sql
   UPDATE booking
   SET payment_status = 'cancelled', updated_at = now()
   WHERE id = ANY($ids)
     AND organization_id = $orgId
     AND payment_status = 'payment_pending'  -- re-check: chroni przed race condition z webhookiem
     AND created_at < now() - interval '15 minutes'
   ```
4. **Audit:** `booking.expire_pending` z `SYSTEM_ACTOR`, dla każdego anulowanego bookingu.

### TTL: 15 minut

Stała `PENDING_PAYMENT_TTL_MS = 15 * 60 * 1000`. Stripe Checkout ma własny timer, ale nie gwarantuje webhooka `checkout.session.expired`.

### Kluczowe wykluczenie

Booking powiązany z aktywnym `group_change_request` (`status = 'awaiting_payment'`) NIE jest anulowany — ma własny 24h TTL przez `groupChangesExpireHandler`.

**Grep potwierdzający:** `payment_pending` ustawiany jest tylko w:
- `bookings/create.ts:271` — bezpośredni booking online
- `bookings/change-group-admin.ts:239` — group change z dopłatą

Bez wykluczenia, booking z group change z `payment_pending` zostałby anulowany po 15 minutach, zamiast czekać 24h na `groupChangesExpireHandler`.

### Harmonogram

Job wywoływany hourly (nie daily). Dedupe key: `bookings.release_expired_pending:${thisHour}`.
Przy 15-min TTL, hourly cron daje maksymalne opóźnienie zwolnienia ~1h — akceptowalne.

Świadomie pominięta w MVP. Klient widział Stripe Checkout — wie, że nie dokończył płatności. Dodanie emaila nie wymaga zmiany schematu; można dorzucić w retrofiku.

## Faza 32 — Custom domains: model + DNS + Caddy webhook

**Status:** ✅ zakończona (2026-07-27)
**Cel:** Enterprise feature — klient podpina własną domenę (np. `zajecia.szkola.pl`). Caddy z `on_demand_tls` + host rewrite.
**Zależności:** Żadna — niezależna od CMS. Stack wymaga VPS z Caddy.
**Migracja:** Nowa tabela `custom_domain` + RLS.

### Architektura (host rewrite przez Caddy)

```
Klient → zajecia.szkola.pl → DNS CNAME → langlion.pl → Caddy
  → Caddy pyta GET /api/custom-domains/verify-tls?domain=zajecia.szkola.pl
  → Jeśli 200: Caddy wydaje certyfikat LetsEncrypt (on_demand_tls)
  → Caddy przepisuje Host: szkola.langlion.pl (host rewrite)
  → Next.js widzi subdomenę — działa identycznie jak dla tenantów bez custom domain
```

**Dlaczego host rewrite, a nie passthrough:**
Next.js Server Actions porównują `Origin` z `Host`. Gdyby aplikacja widziała `zajecia.szkola.pl`, musielibyśmy dynamicznie zarządzać `serverActions.allowedOrigins` — co jest niemożliwe bez proxy. Caddy przepisując Host eliminuje ten problem całkowicie. Aplikacja **nie wie** o custom domain.

**Konsekwencja:** Faza 32 nie wymaga:
- Zmiany w `parseHost` (pure, bezstanowe — pozostaje bez zmian)
- Zmiany w `proxy.ts` / middleware
- Zmiany w `servedOrganization` / `servedSubdomain`
- Zmiany w `next.config.ts` / `serverActions.allowedOrigins`
- `isCloudflareProxy()` — niepotrzebne (Caddy jest naszym proxy)

### Model danych

**Tabela ON DELETE:**

| FK | ON DELETE | Uzasadnienie |
|----|-----------|-------------|
| `custom_domain.organization_id → organization` | CASCADE | Domena bez akademii bezprzedmiotowa |

```sql
CREATE TABLE custom_domain (
  id TEXT PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id TEXT NOT NULL REFERENCES organization(id) ON DELETE CASCADE,
  domain TEXT NOT NULL UNIQUE,
  status TEXT NOT NULL DEFAULT 'pending',    -- 'pending' | 'active' | 'failed'
  verification_token TEXT NOT NULL,          -- unikalny per domain
  verified_at TIMESTAMPTZ,
  last_checked_at TIMESTAMPTZ,              -- aktualizowane przy ręcznej re-weryfikacji
  last_error TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),

);
```

### Flow weryfikacji DNS

1. Owner akademii podaje domenę w panelu (`settings/custom-domain`)
2. Backend: generuje `verification_token`, tworzy rekord `status = 'pending'`
3. Panel: "Dodaj rekord CNAME: `{domena}` → `{subdomain}.langlion.pl`"
4. Caddy: `on_demand_tls` z webhookiem `GET /api/custom-domains/verify-tls?domain=...`. Przy pierwszym requeście, Caddy pyta webhook → jeśli 200, wydaje certyfikat.
5. Owner klika "Zweryfikuj": backend sprawdza CNAME przez `node:dns.promises.resolveCname(domain)` → oczekiwany cel: `{subdomain}.langlion.pl`
6. Sukces → `status = 'active'`, `verified_at = now()`
7. Fail → `status = 'failed'`, `last_error = '...'`
8. Po aktywacji: Caddy przy requeście dostaje 200 → certyfikat → host rewrite → działa

### Webhook Caddy (publiczny endpoint TLS verification)

`GET /api/custom-domains/verify-tls?domain=zajecia.szkola.pl`

Logika:
1. Normalizuj domenę (lowercase, trim)
2. Lookup `custom_domain` WHERE `domain = $1 AND status = 'active'`
3. JOIN `organization` WHERE `deletedAt IS NULL` — soft-deleted org nie dostaje certyfikatu
4. Znaleziono → 200 `{ "allowed": true }`
5. Nie znaleziono → 404 (Caddy nie wyda certyfikatu)

**Endpoint jest publiczny (Caddy nie ma sesji)** — bezpieczny, bo jedyne co zdradza to czy domena istnieje. Timing oracle: obie ścieżki robią pełny lookup DB, brak różnicy czasu.

**Status:** ✅ zakończona (2026-07-27)
**Cel:** Payload Admin przestaje wyglądać jak gołe demo — własny Nav/Logo/SCSS pod branding produktu, oraz natywny Live Preview przez Next.js Draft Mode zamiast gołego `?preview=true` (bezpieczeństwo: US-C1.1/AC2).
**Zależności:** Faza 30b (renderer, pages.ts), Faza 30d (komplet bloków core+custom).
**Migracja:** `versions: { drafts: true }` dodane do kolekcji `pages` — Payload wygeneruje migrację przy najbliższym uruchomieniu.

### 🔑 Kluczowa decyzja bezpieczeństwa: Next.js Draft Mode, nie `?preview=true`

Odrzucone: `searchParams.preview === "true"` otwierałoby dziurę US-C1.1/AC2 — każdy anonim z URL-em może zobaczyć niepublikowaną treść.

Zastosowano: **Next.js Draft Mode** z podpisanym httpOnly cookie.

**Flow:**
1. `admin.preview` na `pages.ts` generuje URL: `{subdomain}.{root}/api/draft?secret={PAYLOAD_DRAFT_SECRET}&slug={slug}`
2. `/api/draft/route.ts` — weryfikuje sekret → `requireOrgPermission("cms.manage")` → `draftMode().enable()` → redirect na `/{slug}`
3. `[...cmsSlug]/page.tsx` — sprawdza `(await draftMode()).isEnabled`, nie `searchParams`
4. `/api/draft/disable/route.ts` — disable z guardem `cms.manage` (chroni UX admina przed przypadkowym wyłączeniem)

**RBAC w rendererze:** `draftMode().isEnabled` NIE sprawdza RBAC — to celowe. Guard jest wykonany w `/api/draft` przy wydaniu cookie. Renderer tylko sprawdza obecność podpisanego cookie (httpOnly, signed przez Next.js).

### Rozstrzygnięcie: `status` vs `versions.drafts`

Role rozdzielone — jeden przełącznik widoczności:

| Mechanizm | Rola |
|-----------|------|
| `status` (pole biznesowe) | Jedyny przełącznik widoczności publicznej |

## Uzupełnienie po domknięciu — Montaż Payload Admin UI (2026-07-27)

**Kontekst:** Fazy 30a–30e oznaczone jako "zakończone" — jednak panel administracyjny Payloada (`@payloadcms/next`) nigdy nie został zamontowany w App Routerze. Wszystkie komponenty były gotowe (config, auth strategy, kolekcje, branding admina), ale brakowało catch-all route, która by je wyrenderowała. Link "Strony" w dashboardzie akademii (`academy-home.tsx`) wskazywał na `/admin`, który (a) był oznaczony jako `"apex"` w `reserved-slugs.ts` → proxy redirect na apex → 403 `requireSuperAdmin()`.

**Przyczyna:** Payload 3 wymaga osobnej grupy tras (`(payload)`) poza `[locale]` — `RootLayout` renderuje własne `<html>`/`<body>` i nie może być zagnieżdżony w istniejącym layoutcie głównym. `@payloadcms/next` był zainstalowany (`v3.86.0`) ale nigdy zaimportowany.

**Zrealizowany zakres:**

| Zmiana | Plik(i) | Uzasadnienie |
|--------|---------|-------------|
| Payload admin catch-all | `src/app/(payload)/admin/[[...segments]]/{layout,page,not-found}.tsx` | `RootLayout` + `RootPage` + `NotFoundPage` z `@payloadcms/next` |
| Payload REST API | `src/app/(payload)/api/payload/[...slug]/route.ts` | `REST_GET/POST/...` z `@payloadcms/next/routes` pod `/api/payload/...` (bez kolizji z istniejącymi `/api/auth/*`, `/api/billing/*`, itd.) |
| Import map | `src/app/(payload)/admin/importMap.ts` | Mapuje ścieżki komponentów brandingu (AdminLogo, AdminIcon, AdminNav) na rzeczywiste React components |
| `routes.api` | `src/features/cms/payload-config.ts` | `/api/payload` — bez kolizji z istniejącymi API route'ami |
| `admin: "both"` | `src/features/cms/reserved-slugs.ts` | Tenant → Payload admin (bare `/admin`), Apex → Super Admin (`/{locale}/admin`). Istniejący mechanizm "both" (F4.6) — nie nowa gałąź logiki |
| Proxy locale exception | `src/proxy.ts` (~linia 421) | Tenant host + `/admin` → pominięcie locale redirect (Payload admin nie używa prefiksu locale). Fall-through przez "both" → forward z `x-org-subdomain` |
| Link "Strony" | `src/app/[locale]/(app)/dashboard/academy-home.tsx` | `<a href="/admin">` zamiast `<Link>` z next-intl (który dodałby prefiks locale) |

**Architektura:** Payload admin dostępny pod bare `/admin` (bez prefiksu locale) na subdomenie tenanta. Super Admin dostępny pod `/{locale}/admin` na apeksie. Rozróżnienie wynika z obecności prefiksu locale — dwa różne wzorce URL, dwa inne route grupy w App Routerze (`(payload)/admin/[[...segments]]` vs `[locale]/(admin)/admin/`). Proxy nie dodaje prefiksu locale dla `/admin` na tenantach, ale dodaje go normalnie dla pozostałych ścieżek i dla `/admin` na apeksie.

**Flow:** `vivamoda.langlion.pl/admin` → proxy (`host=tenant`, `pathname=/admin`) → locale redirect pominięty → `admin: "both"` fall-through → session check → `forward()` z `x-org-subdomain: vivamoda` → App Router: `(payload)/admin/[[...segments]]` → `payload-auth-strategy.ts` czyta nagłówek → resolve org → membership check → panel Payloada.

**RBAC:** Pierwsza linia obrony — proxy wymaga sesji (default-deny). Druga — `payload-auth-strategy.ts` weryfikuje membership w organizacji. Trzecia — `cms.manage` guard w server actions (IDOR).
